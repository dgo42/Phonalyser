Audio backends

A backend is the application's route to a converter: the engine that opens the device, moves the samples and reports the errors. It is chosen under Preferences ▸ Audio, and which backends the list offers depends on the operating system. How a backend works inside - callbacks, ring buffers, exclusive modes - is described in Theory ▸ Audio backend; this page is the practical half: what exists where, and what the application does to the hardware volume on your behalf.

Which backend on which system

Hardware volume on Linux and macOS

A card's hardware volume sits INSIDE the calibrated chain: a control away from where it stood during calibration scales every sample, and nothing in the reading says so. On Linux and macOS the application therefore manages the opened device's own volume itself:

  • At open, the device's volume controls are set to the device's own 0 dB - read from the control's dB scale on Linux, and through the CoreAudio dB translation on macOS. 0 dB is not the same as "maximum": on a capture side the top of the slider is the top of the GAIN range (one bench interface reads +12 dB there), and only the dB scale says where unity really is. A control that publishes no dB information is set to full scale.
  • Only the opened device and direction are touched - never another card, never the other direction, never a port that is not the one in use. On a card that names one stream control per PCM pair identically, the control whose index matches the opened PCM device is taken.
  • At stop, everything the open moved is put back exactly as it was found. A control you move yourself while the stream runs keeps your value.
  • Every failure is loud and none blocks a measurement: a control that cannot be read, mapped or written is named in the log and left alone, and the capture or tone starts anyway.
Windows is different on purpose. There the system volume is part of the calibration: set it once, calibrate, and leave it - the application does not touch it.

macOS: capture glitches on some devices

Some USB devices tear the CAPTURE stream on macOS at operating-system level: every capture shows ringing bursts and discontinuities while the analog output measures perfectly clean, and the very same recording made with Apple's own tools carries the same tear. One example bench device is the Cubilux CB5 - but the incompatibility is a property of the device-and-macOS pairing and can happen with other devices too. The same device may work flawlessly on Linux and Windows.

The workaround is an Aggregate Device. In Audio MIDI Setup create an aggregate and put the device's input and output into it, then select the aggregate in Phonalyser. The aggregation layer adds the stream handling the device's own path lacks, and the captures come out clean.

Important: uncheck "Drift Correction" for the sub-devices of the aggregate. With it, macOS resamples the streams to align their clocks - an alignment that is NOT synchronized to the source the way the measurement itself is - and that resampling shows up as frequency leakage in the spectrum.

An aggregate publishes no volume controls of its own; the application pins and restores the volumes of its MEMBER devices instead, so the 0 dB discipline above holds through the aggregate too.
