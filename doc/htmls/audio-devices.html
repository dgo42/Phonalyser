Browser audio device probe

Enumerates input / output audio devices and probes which sample rates the browser will actually grant. Bit depth is not exposed by the Web platform (Web Audio is 32-bit float after the OS mixer), and there is no exclusive mode - so this shows the ceiling a pure browser tab can reach, not what the hardware can do.

Click Scan and allow microphone access - without permission the OS hides device labels. The scan opens each input device once per candidate rate, so it takes a few seconds.

2. Input sample-rate probe (getUserMedia + track.getSettings())

For each input device we request sampleRate: {exact: r} and report the rate the browser actually granted. ✓ = granted at the requested rate, ≈ = opened but resampled to a different rate, ✗ = refused.

3. Output / AudioContext sample-rate support (new AudioContext({sampleRate}))

Probes the default output path - a browser tab cannot enumerate per-output-device capabilities, only attempt a context at a given rate.

3b. Per-output probe (new AudioContext({sinkId}))

Where the engine implements the sinkId context option (Chromium 110+), a context can be OPENED on a specific output sink - which makes the sink's own default rate and a rate grid probeable after all, the closest a tab gets to section 2 for outputs. The binding is verified through ctx.sinkId: an engine that predates the option ignores the unknown dictionary member and would silently re-probe the default path instead. ok = granted at the requested rate, ~n = opened but running at n, x = refused, (default path) = the option was ignored. A missing device here is missing one layer LOWER: the browser only ever sees the sound server's sinks - a card whose output profile is off (or whose playback is held by a direct ALSA client) has no sink to list.

4. Bit-depth probe, per device (sampleSize)

The Media Capture spec lists sampleSize as a constrainable property, so "bit depth is not exposed" deserves measuring rather than asserting. Each INPUT is opened in turn and asked what depth it reports and which exact depths it will accept. OUTPUTS cannot be probed at all - a tab may route to one with setSinkId but never open or inspect it - so they are listed for completeness with the reason.

5. What the platform does NOT expose

  • Bit depth - partly, and less than it looks. Chromium DOES implement the sampleSize constraint: it advertises it, getCapabilities() returns a min/max, and an exact value outside that range is refused with OverconstrainedError rather than ignored (measured - run section 4). What it describes is the capture format the browser opened, NOT a choice you can make: the samples handed to the page are float32 taken post-mixer, so the device's own converter depth is already gone by the time anything is read. Treat a reported depth as information, not control.
  • Exclusive mode - none. Every stream goes through the shared OS mixer + its resampler.
  • Per-output-device formats - depth: never. Rates: probeable only through the sinkId context option where implemented (section 3b); elsewhere setSinkId only routes.
