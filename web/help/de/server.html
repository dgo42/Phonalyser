Der Phonalyser-Server

Die Maschine, an der Ihre Messhardware hängt, muss nicht die Maschine sein, an der Sie sitzen. Lassen Sie den Phonalyser-Server auf derjenigen laufen, an der die Wandler tatsächlich hängen, und sie wird zum Messplatz: Ihr gehören die Soundkarten und der QA40x-Analysator, und sie bietet sie über das Netz den Phonalyser.web-Clients anderswo an. Er hat kein Fenster und braucht keine Arbeitsoberfläche - ein Raspberry Pi oder eine beliebige kopflose Kiste genügt.

Dieses Kapitel ist die Server-Hälfte: einen ans Laufen bringen und am Laufen halten. Die Client-Hälfte - einen Messplatz finden, sich mit ihm verbinden und über ihn messen - steht unter Einstellungen ▸ Messen über einen Phonalyser-Server, und was dabei über die Leitung geht, unter Funktionsprinzip ▸ Ein Messplatz im Netz.

Was er ist und was Sie brauchen

Der Server wird als eigener Download ausgeliefert, ein ZIP je Plattform - Windows x64 und x86, Linux x86_64 und aarch64, macOS Intel und Apple Silicon - neben den Installationspaketen der Desktop-Anwendung. Entpacken Sie es irgendwohin und starten Sie es; es gibt kein Installationsprogramm, und außerhalb des Ordners wird nichts geschrieben, bis der Server startet.

In jedem ZIP steckt ein einziges Fat-JAR samt den Startern für diese Plattform. Mitbringen müssen Sie eine Java-Laufzeitumgebung ab Version 17 im PATH - und sonst nichts: Eine JRE ist nicht enthalten.

PlattformWas dabei ist
Windows phonalyser-server-x64.exe (Starter zum Doppelklicken), phonalyser-server.cmd (dasselbe in einer Konsole, die Sie mitlesen können), install-service.cmd / uninstall-service.cmd sowie ein Ordner natives\ mit PortAudio (dem WDM-KS-Weg), libusb (dem QA40x) und csjsound (den WASAPI-exklusiven JavaSound-Mixern). Lassen Sie natives\ neben dem Starter liegen - nur dort wird gesucht. Ohne csjsound läuft der Server zwar weiter, bietet aber nur Mixer im Shared-Modus an, sodass die EXCL:-Geräte und die von ihnen abhängigen hohen Abtastraten aus der Liste verschwinden.
Linux phonalyser-server.sh, phonalyser-server-service.sh und die QA40x-udev-Regel 70-qa40x.rules. Ein natives/ gibt es hier bewusst nicht: ALSA wird über die Java-Laufzeitumgebung erreicht, und libusb - nur für ein QA40x nötig - kommt aus Ihrer Distribution. Das JAR ist architekturneutral - die ZIPs für x86_64 und aarch64 unterscheiden sich nur im Namen.
macOS phonalyser-server.sh, phonalyser-server-service.sh und ein natives/ mit libportaudio.dylib (CoreAudio) und libusb-1.0.dylib. Die ZIPs für Intel und Apple Silicon tragen unterschiedliche dylibs - nehmen Sie das zu Ihrem Mac passende. Ein QA40x braucht hier keinen Kernel-Treiber.
Windows: Das Suffix -x64 / -x86 benennt, worauf das Bündel zielt - welche JRE der Starter sucht und für welche Architektur die DLLs in natives\ sind - nicht die Bitbreite des Starters selbst. Das 32-Bit-Bündel besteht auf einer 32-Bit-JVM, weil eine 64-Bit-JVM stillschweigend keine seiner DLLs fände, und es begrenzt den Heap auf 1200 MB, so viel wie ein 32-Bit-Prozess zuverlässig reservieren kann. Ein QA40x muss bereits an den WinUSB-Treiber gebunden sein, was geschieht, sobald QuantAsylums eigene Software auf dieser Maschine gelaufen ist.
Betreiben Sie den Messplatz auf einer physischen Maschine, nicht in einer virtuellen. Ein Server, der in einer virtuellen Maschine gemessen hat, zeigte starke periodische Aussetzer in beiden Richtungen; dieselbe Hardware auf einer physischen Maschine mass sauber. Das Audiogerät wird über USB erreicht, und es ist die virtualisierte USB-Zeitsteuerung des Gastsystems, die bricht: die Samples treffen verspätet und stossweise ein, was eine Messung als Lücken im Signal liest. Nichts im Server kann das ausgleichen - stellen Sie den Messplatz auf echte Hardware.

Betrieb in einer Konsole

    phonalyser-server-x64.exe
    phonalyser-server.cmd --name bench1 --port 8377
    ./phonalyser-server.sh
    ./phonalyser-server.sh --name bench1 --port 8377

Jeder Starter nimmt dieselben vier Argumente:

FlagBedeutung
--name <text> Der Name, den Clients in ihrer Server-Liste sehen und im Hinweis belegt von neben einem Gerät, das jemand anders hält. Voreinstellung ist der Hostname der Maschine.
--port <port> Ein Port trägt alles - den Steuerkanal, den Audiostrom, die informativen Endpunkte, den Datei-Upload und das Web-Bundle. Standard 8377.
--bind <address> Nur auf einer Schnittstelle lauschen. Voreinstellung: auf allen. Das ist der eine Stellhebel, der begrenzt, wer den Messplatz erreichen kann - siehe keine Authentifizierung weiter unten.
-d, --daemon Wird angenommen, und jede Dienstdefinition übergibt es - ändert heute aber nichts: Der Server schreibt in keinem Modus auf die Konsole, und die Protokolldatei wird mit wie ohne das Flag gleich geschrieben.

Strg-C stoppt ihn sauber. Die Abschaltroutine schließt die Audio-Leitungen und parkt einen QA40x-Analysator in einer sicheren Abschwächerstellung - derselbe Schutz, den die Desktop-Anwendung beim Beenden ausführt. Deshalb wird ein Server gestoppt statt abgeschossen: Ein "Task beenden" lässt den Analysator in dem empfindlichen Eingangsbereich stehen, den die letzte Messung gewählt hat.

macOS fragt einmal. Wenn der Server zum ersten Mal einen Eingang öffnet, fragt macOS nach dem Mikrofonzugriff. Erteilen Sie ihn, sonst bleibt jede Aufnahme stumm (Systemeinstellungen ▸ Datenschutz & Sicherheit ▸ Mikrofon).

Die Suche und die Firewall

Clients finden einen Server über UDP-Multicast an 239.255.83.77, Port 8377/udp - dieselbe Zahl, auf der der Server lauscht, denn UDP und TCP haben getrennte Portbereiche. Die Ankündigung ist link-lokal: Router reichen sie nicht weiter, sodass ein Messplatz in einem anderen Subnetz nie gefunden und im Client stattdessen über seine Adresse hinzugefügt wird.

Lassen Sie diesen einen Port durch die Firewall, udp und tcp, oder verzichten Sie ganz auf die Suche und tippen Sie die Adresse im Client von Hand ein.

Betrieb als Dienst

Windows - ein echter Dienst

Aus einer erhöhten Eingabeaufforderung:

    install-service.cmd                     als LocalSystem betreiben
    install-service.cmd /user BENCH\alex    unter einem echten Konto betreiben
    install-service.cmd /user BENCH\alex --name bench1

Zusätzliche Argumente werden in den Dienst eingebacken. Er heißt PhonalyserServer und zeigt auf jenen Ordner, der danach also weder verschoben noch gelöscht werden darf. Es ist ein echter Dienst der Dienststeuerung (Service Control Manager), betrieben von WinSW: ihn zu stoppen ist eine Bitte, kein Abschuss - WinSW sendet ein Strg+C und wartet bis zu 20 Sekunden, sodass die Abschaltroutine läuft und der Analysator geparkt wird, was eine geplante Aufgabe oder ein "Task beenden" nicht täten.

    starten    : sc start PhonalyserServer
    stoppen    : sc stop PhonalyserServer
    entfernen  : uninstall-service.cmd
    einstellen : services.msc, Eintrag "Phonalyser server"
Welches Konto, und warum das zählt. Ein Windows-Dienst läuft immer in Sitzung 0, nie in Ihrer Desktop-Sitzung - eine Eigenschaft des Betriebssystems, nicht dieses Servers. Ein QA40x wird über USB erreicht und stört sich nicht daran, LocalSystem genügt also. Soundkarten stört es sehr wohl: Welche Endpunkte eine Anwendung sieht und welcher davon der Standard ist, steht im benutzerbezogenen Teil der Registry, und LocalSystem hat dort seine eigene, praktisch leere Sicht. Installieren Sie mit /user <account>, damit der Dienst das Profil jenes Benutzers lädt und dieselben Geräte sieht wie er. Windows verlangt das Kennwort des Kontos, bevor ein solcher Dienst starten kann, und das Skript geht bewusst nicht mit Kennwörtern um: Öffnen Sie nach dem Installieren services.msc ▸ Phonalyser server ▸ Eigenschaften ▸ Anmelden ▸ Dieses Konto, tippen Sie es ein und starten Sie dann. Zeigt selbst das die erwartete Karte nicht, kämpfen Sie nicht mit dem Dienst - legen Sie eine Verknüpfung zum Starter in shell:startup, und er startet bei der Anmeldung in Ihrer eigenen Desktop-Sitzung, wo der Audio-Stapel eindeutig ist.

Linux - eine systemd-Unit

    sudo ./phonalyser-server-service.sh install
    sudo ./phonalyser-server-service.sh activate
    sudo ./phonalyser-server-service.sh install --name bench1 --bind 192.168.1.20

install schreibt /etc/systemd/system/phonalyser-server.service mit Verweis auf jenen Ordner, legt den Systembenutzer phonalyser an, erstellt /var/lib/phonalyser und /var/log/phonalyser und installiert die QA40x-udev-Regel; activate aktiviert die Unit und startet sie. Zusätzliche Argumente an install werden in die Unit eingebacken, und der Ordner darf danach nicht verschoben werden - die Unit zeigt direkt auf ihn.

    status    : systemctl status phonalyser-server
    stoppen   : sudo systemctl stop phonalyser-server
    entfernen : sudo ./phonalyser-server-service.sh uninstall

Der Dienstbenutzer erhält die Gruppen audio und plugdev durch die Unit selbst, sodass an /etc/group nichts geändert wird. systemctl stop sendet SIGTERM, sodass die Abschaltroutine läuft und der Analysator geparkt wird. uninstall lässt /var/lib/phonalyser, /var/log/phonalyser und das Konto unangetastet: Ihre Kalibrierung ist Datenbestand, keine Paketierung.

macOS - ein LaunchAgent je Benutzer

    ./phonalyser-server-service.sh install
    ./phonalyser-server-service.sh activate

Kein sudo verwenden. install schreibt einen LaunchAgent nach ~/Library/LaunchAgents/org.edgo.phonalyser.server.plist mit Verweis auf jenen Ordner; activate lädt ihn, und von da an startet er bei jeder Anmeldung.

    status    : launchctl print gui/$(id -u)/org.edgo.phonalyser.server
    stoppen   : launchctl bootout gui/$(id -u)/org.edgo.phonalyser.server
    entfernen : ./phonalyser-server-service.sh uninstall
Ein LaunchAgent, kein LaunchDaemon - und das ist keine Bequemlichkeit. CoreAudio arbeitet je Sitzung, und die Nachfrage nach dem Mikrofonzugriff kommt vom Window-Server: Ein Systemdienst zählte überhaupt keine Eingänge auf und könnte die Nachfrage nie beantworten. Der Preis dafür, es richtig zu machen, ist, dass der Server nur läuft, solange Sie angemeldet sind. bootout beendet ihn normal, sodass die Abschaltroutine läuft und der Analysator geparkt wird.

Wo was liegt

PlattformProtokoll, Karten und Kennung
Windows Ein Ort, gleich wie er gestartet wurde - Konsole, LocalSystem-Dienst oder /user-Dienst gleichermaßen: %ProgramData%\Phonalyser\logs\phonalyser-server.log, %ProgramData%\Phonalyser\devices.yaml, %ProgramData%\Phonalyser\server-id. WinSW führt im selben Ordner logs sein eigenes Verzeichnis der Dienststarts und -stopps, neben dem Protokoll der Anwendung statt an dessen Stelle.
Linux Aus einem Terminal: ~/.config/Phonalyser/logs/phonalyser-server.log (oder /var/log/phonalyser, wenn dort geschrieben werden darf). Als Dienst: /var/log/phonalyser/phonalyser-server.log und /var/lib/phonalyser für devices.yaml und server-id - das Konto phonalyser hat kein eigenes Heimatverzeichnis, daher benennt die Unit diese Pfade.
macOS Beide Startarten verwenden ein Verzeichnis: ~/Library/Application Support/Phonalyser/ - logs/phonalyser-server.log, devices.yaml, server-id.

Unter Windows ist dieses eine maschinenweite Zuhause Absicht: Ein Server ist eine Maschineninstallation. Das benutzerbezogene %APPDATA%\Phonalyser gehört der Desktop-Oberfläche, und ein Server, der es mitbenutzte, bearbeitete den Kartenspeicher der Desktop-Anwendung - während die beiden Dienstformen jeweils ein anderes %APPDATA% bekämen und dem Konsolenlauf widersprächen.

Die Folge, die man sich merken muss: Die Kalibrierung der Desktop-Anwendung ist nicht das, was der Server ausliefert. Geben Sie dem Server seine eigene - kalibrieren Sie über einen verbundenen Client, was direkt in den Speicher des Messplatzes schreibt (siehe Karten und Kalibrierung auf dem Messplatz), oder kopieren Sie devices.yaml hinüber. Unter Linux gilt dasselbe zwischen einem Terminal-Lauf und dem systemd-Dienst, die getrennte Datenverzeichnisse haben.

Es gibt keine Authentifizierung, und das mit Absicht

Ein Phonalyser-Server fragt nicht nach einem Kennwort, und nichts auf der Leitung ist verschlüsselt. Das ist eine Entscheidung, kein Versäumnis: Ein Messgerät gehört in ein Netz, dem Sie vertrauen - den Raum, in dem Ihre Messtechnik steht - und Zugangsdaten in einem LAN-Instrumentenprotokoll brächten nichts, was das Netz nicht schon leistet. Wer den Port erreicht, kann die Geräte auflisten und eines belegen.

Stellen Sie den Port also nicht ins offene Internet. Hat die Maschine mehr als eine Schnittstelle, binden Sie den Server mit --bind an diejenige, an der Ihr Messplatz hängt, und lassen Sie den Rest unerreichbar.

Über ihn messen

Läuft ein Server, sind es auf der Client-Seite drei Schritte, und alle stehen in Einstellungen ▸ Audio:

  1. Den Messplatz finden. Server... öffnet die Liste. Im Browser öffnet sie sich leer - eine Seite kann die Multicast-Ankündigung des Servers nicht hören -, tragen Sie also Host und Port dieses Messplatzes unter Server manuell hinzufügen ein; von dieser einen Adresse aus bringt seine Peer-Tabelle die übrigen mit. Verbinden - oder ein Doppelklick auf die Zeile - öffnet die Sitzung.
  2. Ein Backend wählen. Die Backends des Messplatzes reihen sich in die Backend-Liste neben die lokalen ein, geschrieben als <Server> -> <Backend>. Das Durchsehen ist nur eine Vorschau; OK übernimmt.
  3. Messen. Von da an verhalten sich die Gerätelisten, der Kartenbereich, die Auswahlknöpfe für den Bereich, QA40x-Einstellungen, der Generator, die Sweeps und Abspielen aus... genau wie bei lokaler Hardware. Die Kalibrierung gehört zum Messplatz, eine Fadenkreuz-Kalibrierung schreibt also in dessen Speicher.

Die Einzelheiten - was vorgemerkt wird und was sofort wirkt, der Hinweis belegt von an einem Gerät, das ein anderer Client hält, die Regel der gewährten Rate, der Datei-Upload, der Wiederaufbau alle fünf Sekunden und die Gründe, aus denen eine Sitzung enden kann - stehen alle unter Einstellungen ▸ Messen über einen Phonalyser-Server.

Der Server liefert auch die Anwendung aus

Auf der Maschine, von der aus Sie messen, muss nichts installiert werden. Ein laufender Server gibt seine eigene Kopie von Phonalyser.web heraus: Öffnen Sie die Adresse des Messplatzes in einem Chromium-Browser - http://<Messplatz>:8377/ - und Sie erhalten einen Arbeitsplatz, der bereits mit ihm verbunden ist, die Backends dieses Messplatzes anbietet und gar keine Einrichtung braucht. Das ist die Adresse, die man einer Kollegin gibt.

Eine solche Seite hat keine lokalen Backends - sie kommt über einfaches http://, was kein sicherer Kontext ist, sodass die Audioaufnahme des Browsers und WebUSB dort nicht existieren. Das ist zugleich die Antwort auf eine Falle des anderen Wegs: Eine über https:// geladene Anwendung kann überhaupt keine Sitzung zu einem Messplatz im LAN öffnen. Beides steht in Phonalyser im Browser ▸ die Seite, die ein Messplatz ausliefert.

Während er läuft

  • Die Hardware wird alle zwei Sekunden neu aufgezählt, sodass ein am Messplatz eingestecktes oder abgezogenes Gerät bemerkt wird, ohne irgendetwas neu zu starten, und jeder verbundene Client davon erfährt. Zwei Sekunden statt fortlaufend, und zwar mit Absicht: Das Aufzählen spricht mit Treibern und mit USB, und nichts an einem Messplatz erscheint so dringend, dass die Verzögerung eine Messung kostete.
  • Ein Client je Gerät zur Zeit. Der Server hält eine Sperre je Gerät, sodass zwei Bedienende einander nicht in die Messung reden; die Sperre nennt ihren Halter, und genau das liest der Client als belegt von.
  • Er bedient alle seine Backends gleichzeitig. Auf einem Server gibt es kein globales "aktives Backend" - jede Sitzung wählt ihr eigenes, sodass ein Client am QA40x sein kann, während ein anderer an einer Soundkarte misst.
  • Das Herunterfahren parkt die Hardware, den Eingangsabschwächer des QA40x eingeschlossen, genau wie es die Desktop-Anwendung beim Beenden tut.
  • Liegt neben dem JAR ein Ordner namens web, bedient der Server auch ihn, über denselben HTTP-Port.
